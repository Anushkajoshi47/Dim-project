# KJS-SRS-01 — SomaiyaSat & SomaiyaPod Mission Control

A realtime mission-control dashboard for an academic PocketQube mission concept:
two simulated spacecraft in a low-Earth leader–follower formation, an amateur
radio payload with four operating modes, and an autonomous inter-satellite
routing engine that chooses how to get data to the ground.

> ## ⚠️ This is a simulation. It is not connected to anything.
>
> There is **no real satellite, no real RF hardware, no real ground station and
> no real radio link** anywhere in this project. Every number the dashboard
> displays — orbit position, battery voltage, temperature, RSSI, Doppler shift,
> routing decision — is generated by simulation code in `backend/src/sim/` and
> streamed to the browser. The mission designator, the spacecraft and the
> ground station are all fictional. Nothing here transmits, receives, or
> commands anything.
>
> It is built to be *physically plausible*, which is exactly why this notice
> matters: the values are realistic enough to be mistaken for real telemetry.
> The dashboard carries the same disclosure permanently in its footer.

## Quick start

Requires **Node.js ≥ 18.18** and **Docker** (for PostgreSQL).

```bash
# 1. install both workspaces
npm install

# 2. start PostgreSQL (host port 5544, chosen to avoid a local install on 5432/5433)
docker compose -f backend/docker-compose.yml up -d

# 3. create the schema
npm run db:migrate

# 4. run backend + frontend together
npm run dev
```

Then open **<http://localhost:3000>**.

| | |
|---|---|
| Dashboard | <http://localhost:3000> |
| Simulation API | <http://localhost:4000/api/health> |

Steps 2–3 can be run in one go with `npm run setup`.

### Running without Docker

If PostgreSQL is unreachable the backend does **not** fail — it logs a warning,
falls back to an in-memory ring buffer for history, and reports
`persistence: "MEMORY"`, which the dashboard footer displays. Everything except
*history surviving a backend restart* still works. The supported path is
PostgreSQL; the fallback exists so a demo is never blocked by a missing daemon.

### Network note

The map uses CARTO's public dark basemap tiles, so the world imagery needs
internet access. Without it the map still renders correctly — a 30° graticule,
both ground tracks, the footprint circles, the ground station and both
spacecraft markers are all drawn locally as vectors; only the raster landmass
imagery is missing.

## Deployment

**This backend cannot go on Vercel, Netlify, or any serverless platform.** It
keeps a persistent socket.io server open and runs the simulation on
`setInterval` loops inside one long-lived process; serverless functions are
request-scoped and would kill both. It needs a host that runs a normal
always-on Node process.

A `render.yaml` blueprint in the repo root deploys the database, backend and
frontend together on [Render](https://render.com). The frontend alone can go on
Vercel instead if preferred — only the backend has the long-running constraint.

### Required environment variables

| Service | Variable | Value |
|---|---|---|
| backend | `DATABASE_URL` | Postgres connection string |
| backend | `CORS_ORIGIN` | Frontend origin(s), comma-separated |
| backend | `PORT` | Set by the host automatically |
| frontend | `NEXT_PUBLIC_BACKEND_URL` | Public backend URL |

`NEXT_PUBLIC_BACKEND_URL` is compiled into the browser bundle at **build** time,
so changing it needs a rebuild, not just a restart. `CORS_ORIGIN` accepts a
comma-separated list because the dashboard is served from a different host than
the API, and preview deployments get their own URLs.

### Chicken-and-egg on first deploy

Neither URL exists until the services do. Deploy once, copy the two generated
URLs into the variables above, then redeploy **both** services.

### Free-tier caveats for a live demo

- Free web services **sleep after ~15 minutes idle**. The next request takes
  around a minute to wake, and because simulation state lives in memory, the
  mission restarts from its epoch. **Open the dashboard several minutes before
  a panel demo** so it is warm.
- Free managed Postgres is time-limited on most providers. If it expires, the
  backend does not break — it falls back to in-memory history and says so in the
  footer. Only history across restarts is lost.
- For a demo that must not stall, a paid always-on instance (~$7/mo) removes
  both problems.

### Running it locally for the panel instead

Hosting is optional. `npm run setup && npm run dev` on a laptop gives the full
experience with no cold starts, no free-tier limits and no network dependency
beyond map tiles — which is often the safer choice for a live assessment.

### The engines are chained, not independent

This is the part that makes the simulation cohere rather than being four random
number generators on one screen:

```
orbit (1 Hz) ─────► telemetry (1 Hz) ─────► radio (0.5 Hz) ─────► routing (0.33 Hz)
       │                    │                      │
   eclipse flag       pointing error          link margin
   elevation ─────────────────────────────────────┘
```

Concretely:

- **Eclipse drives power.** The orbit engine's cylindrical shadow test sets the
  sunlit flag; solar array current collapses to leakage, the pack starts
  discharging, and the state-of-charge trace develops its sawtooth. The chart
  shades eclipse periods behind the trace so the causation is visible.
- **Eclipse drives temperature.** All four thermal nodes track a target that
  swings with illumination, through a first-order lag — so temperature can
  never step, only drift.
- **Elevation drives the radio.** RSSI comes out of an actual link budget
  (`EIRP − FSPL − atmospheric − polarisation + G_rx − L_line`), so it rises
  toward zenith and collapses at the horizon because the geometry changed.
  Below the station's 5° minimum elevation the readouts go *no-data* — they do
  not show a plausible-looking number for a spacecraft that is under the
  horizon.
- **ADCS pointing drives both links.** Attitude error feeds polarisation loss on
  the downlink and pointing loss on the S-band crosslink, so a tumbling
  spacecraft measurably degrades its own comms.
- **All of it drives routing.** Link margin, battery headroom, queue depth and
  historical loss are the routing scorer's four features.

### The "AI" routing engine

A transparent weighted heuristic, not a black box and not real ML. Three
candidate routes — direct to ground, relay via SomaiyaPod, store-and-forward —
are scored on four weighted features, and the scores go through a softmax so the
winner's probability is a genuine confidence figure that drops when two routes
are closely matched:

| Feature | Weight |
|---|---|
| Link margin | 0.40 |
| Battery headroom | 0.20 |
| Queue pressure | 0.22 |
| Reliability (historical packet loss) | 0.18 |

Each candidate's per-factor contributions are sent to the browser, so the
dashboard shows **why** a route won, not only which one did. A 5% hysteresis
band stops the router flapping between near-equal options. A natural-language
rationale is generated from the dominant factors.

**The demo moment:** inject *UHF downlink degradation* from the command console
during a pass. SomaiyaSat's own transmitter drops 13 dB, the direct link margin
collapses — but the S-band crosslink and SomaiyaPod's separate downlink are
untouched, so the router reroutes through the relay and recovers the downlink.
When the fault clears it returns to direct. Verified behaviour:

```
 el     satRSSI   SAT_GS  SAT_POD  POD_GS   route           conf
 22.6   -107.4     27.0      6.7    10.8    DIRECT           82%
 19.1   -110.9     25.6      6.7    13.6    DIRECT           80%   ← fault injected
  8.7   -128.3     11.2      6.7    13.5    DIRECT           69%
  4.2       --    -99.0      6.7    10.6    RELAY_POD        77%   ← rerouted
 -6.1       --    -99.0      6.7   -99.0    STORE_FORWARD   100%   ← pass over
```

## Orbit model

`backend/src/sim/orbit.ts` holds every piece of celestial math, isolated so it
can be swapped for a real propagator (SGP4) without touching anything else —
every other engine consumes only the `PropagatedState` it returns.

It is a **simplified circular propagator**, not SGP4. It models:

- circular orbit from altitude / inclination / RAAN / period / epoch phase
- sun-synchronous nodal precession (~1°/day)
- Earth-rotation-corrected ground track via GMST
- low-precision solar ephemeris and a cylindrical eclipse model
- topocentric look angles, range rate, and AOS/LOS by bisection
- inter-satellite line-of-sight with an atmospheric margin

**Two deliberate modelling choices, both documented in code:**

1. **The orbit plane is solved at startup** so SomaiyaSat makes an overhead pass
   ~5 simulated minutes after the epoch. Without this, the plane's orientation
   relative to Mumbai depends on when you happened to start the process, and the
   first usable pass could be hours away.

2. **Both spacecraft share an altitude and period.** This is a stable
   leader–follower formation: SomaiyaPod trails by 9.5° of argument of latitude
   (~1150 km) indefinitely. Give them different altitudes and the phase offset
   grows every orbit until, after a few simulated days, they sit on opposite
   sides of the Earth with the crosslink permanently occulted. Real spacecraft
   would need station keeping; differential drag is not modelled.

### Passes are genuinely infrequent — and that is correct

A sun-synchronous ground track shifts ~24° of longitude west every revolution, so a
single ground station does **not** get a pass every orbit. Real passes come in
clusters of two or three followed by gaps of **ten hours or more**. The pass
predictor therefore sweeps a 30-hour horizon.

This is authentic but unwatchable in a live demo, which is why the command
console has **Skip to next AOS**. It fast-forwards the simulation clock in ~5
simulated-minute chunks, re-running the orbit and telemetry engines on each one,
so the battery genuinely discharges through the intervening eclipses and
temperatures genuinely cycle. It is a fast-forward, not a teleport — no state is
faked.

## Data realism

Rules enforced throughout `backend/src/sim/`:

- **Nothing is ever frozen and no chart is ever a straight line.** Every channel
  carries mean-reverting (Ornstein–Uhlenbeck) sensor noise plus a slower
  physical trend. Even the crosslink margin — which a constant-separation
  formation would otherwise pin to a fixed value — varies with ADCS pointing and
  fading.
- **The noise integrator is exact, not Euler.** The sim clock runs at up to
  240×, so a 1 s wall tick can be a 240 s simulated step. Explicit Euler
  diverges once `theta·dt > 2`; the exact OU discretisation is stable at any
  step size. (This was a real bug — at 30× it produced a 10¹⁵ W bus load.)
- **Physical bounds are enforced on the published value.** ADC noise is added
  *before* the clamp, so battery voltage can never read above the 8.4 V pack
  limit even by a millivolt.
- **Temperatures cannot step.** All thermal nodes move through a first-order lag.
- **No signal below the horizon.** RSSI, SNR and Doppler are `null`, and the UI
  renders no-data, not a number.
- **Timestamps come from the simulation clock**, never `Date.now()`, so
  everything stays internally consistent at any speed multiplier.

## Radio payload

One mode active at a time; switching is a real command round-trip.

| Mode | Downlink | Power | Modulation |
|---|---|---|---|
| FM voice repeater | 435.550 MHz | 0.80 W | FM, V/U crossband |
| APRS digipeater | 145.825 MHz | 0.50 W | AFSK 1200 Bd AX.25 |
| SSTV downlink | 437.400 MHz | 1.20 W | FM SSTV Robot 36 |
| CW telemetry beacon | 437.025 MHz | 0.35 W | CW/OOK 18 WPM |

All frequencies are in the 2 m / 70 cm amateur satellite bands. Doppler is
computed from range rate (`−ṙ/c · f`) and reaches roughly ±9 kHz at 435 MHz,
sweeping through zero at closest approach.

## Command console (mock uplink)

Commands are **not** applied instantly. Each is queued, held for a simulated
1–3 s uplink delay, then executed and acknowledged — the panel shows
`PENDING → ACK` with the measured round-trip. Every command is written to the
`CommandLog` table.

| Command | Effect |
|---|---|
| `SET_RADIO_MODE` | Reconfigure the payload (the round-trip demo) |
| `SKIP_TO_AOS` | Fast-forward to just before the next pass |
| `FORCE_ROUTE_EVAL` | Re-score all routes immediately |
| `TRIGGER_ANOMALY` | Inject one of five faults |
| `CLEAR_ANOMALY` | Clear the active fault |
| `SET_SIM_SPEED` | 1× – 120× (top bar) |
| `RESET_SIM` | Restart from epoch and clear history |

Anomalies also occur spontaneously (~1 per 4 minutes of real time) and always
clear themselves — the demo needs to show degradation *and recovery*.

| Endpoint | Purpose |
|---|---|
| `GET /api/health` | Liveness, sim time, speed, persistence mode |

| `GET /api/history/:channel?minutes=30` | Chart backfill — `power`, `thermal`, `attitude`, `obc`, `orbit`, `radio` |
| `GET /api/events?limit=200` | Event log |
| `GET /api/routing/decisions?limit=100` | Routing decision history |

| `GET /api/radio/modes` · `GET /api/anomalies/catalog` | Reference data |

Socket.io channels: `snapshot` (once, on connect), then `orbit`, `telemetry`,
`radio`, `routing`, `event`, `command`, `command:ack`.

## Persistence

Prisma over PostgreSQL, four tables: `TelemetrySample` (JSON payload per channel,
so an engine can gain a field without a migration), `RoutingDecision`,
`CommandLog`, `EventLog`.

Writes are **buffered and flushed in batches** every 1.5 s, so a 1 Hz telemetry
loop never becomes a round-trip per tick. Charts are backfilled from
`/api/history/:channel` on mount, which is what makes them survive a page
refresh instead of starting empty.

## Design notes

Dark-only operations console: dense, monospace numerics, tabular figures so
digits don't jitter as they update, square corners and hairline rules.

The chart palette was validated with a colour-vision-deficiency checker against
this console's chart surface (`#111820`) — lightness band, chroma floor,
adjacent-pair CVD separation (worst ΔE 8.4 protan), normal-vision separation
(worst ΔE 19.8) and contrast all pass. The four categorical slots are assigned
in a fixed order and never cycled.

Status colours (green/amber/red) are **reserved** for spacecraft state and event
severity, are never reused as a series colour, and never carry meaning without an
accompanying text label and a distinct glyph. The cyan accent is chrome only —
active borders and selected controls — and never appears as a data mark.
